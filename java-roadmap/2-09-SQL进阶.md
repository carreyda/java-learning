## 1. JOIN 深入

### 1.1 JOIN 类型全览

```
INNER JOIN（内连接）：返回两表都匹配的行
LEFT JOIN（左连接）：返回左表所有行，右表没有则 NULL
RIGHT JOIN（右连接）：返回右表所有行，左表没有则 NULL
CROSS JOIN（交叉连接）：笛卡尔积（慎用）
SELF JOIN（自连接）：表和自身连接
```

```sql
-- 图示（以 user 和 article 为例）
-- user: id=1,2,3   article: author_id=1,1,2

-- INNER JOIN：只有 id=1,2 的用户（因为 id=3 没有文章）
SELECT u.username, COUNT(a.id) as cnt
FROM user u INNER JOIN article a ON u.id = a.author_id
GROUP BY u.id;

-- LEFT JOIN：id=1,2,3 都返回，id=3 的 cnt 是 0
SELECT u.username, COUNT(a.id) as cnt
FROM user u LEFT JOIN article a ON u.id = a.author_id
GROUP BY u.id;
```

### 1.2 多表 JOIN

```sql
-- 三表关联：文章 + 作者 + 分类
SELECT
    a.id,
    a.title,
    u.username   AS author,
    c.name       AS category,
    a.view_count,
    a.created_at
FROM article a
JOIN user u         ON a.author_id   = u.id
LEFT JOIN category c ON a.category_id = c.id
WHERE a.status = 'PUBLISHED'
ORDER BY a.created_at DESC
LIMIT 10;
```

### 1.3 自连接（SELF JOIN）

用于查询层级关系（如分类的父子关系、员工的上下级）：

```sql
-- 分类表（支持父子分类）
CREATE TABLE category (
    id        INT PRIMARY KEY AUTO_INCREMENT,
    name      VARCHAR(50) NOT NULL,
    parent_id INT DEFAULT NULL  -- NULL 表示顶级分类
);

-- 查询所有分类及其父分类名称
SELECT
    c.id,
    c.name,
    p.name AS parent_name
FROM category c
LEFT JOIN category p ON c.parent_id = p.id
ORDER BY COALESCE(c.parent_id, c.id), c.id;
```

### 1.4 多对多关联查询

```sql
-- 文章 ↔ 标签（多对多，通过中间表 article_tag）
SELECT
    a.id,
    a.title,
    GROUP_CONCAT(t.name ORDER BY t.name SEPARATOR ', ') AS tags
FROM article a
LEFT JOIN article_tag at ON a.id = at.article_id
LEFT JOIN tag t          ON at.tag_id = t.id
WHERE a.status = 'PUBLISHED'
GROUP BY a.id, a.title
ORDER BY a.created_at DESC;
```

`GROUP_CONCAT` 把多行合并成一个字符串，非常适合多对多的展示场景。

## 2. 子查询进阶

### 2.1 EXISTS vs IN

```sql
-- IN：先执行子查询，得到结果集，再过滤外层
SELECT * FROM user
WHERE id IN (SELECT DISTINCT author_id FROM article WHERE status = 'PUBLISHED');

-- EXISTS：外层每行都执行一次子查询，子查询返回行则保留
SELECT * FROM user u
WHERE EXISTS (
    SELECT 1 FROM article a
    WHERE a.author_id = u.id AND a.status = 'PUBLISHED'
);

-- 性能差异：
-- 子查询结果集小 → IN 更快
-- 外表小、子查询大 → EXISTS 更快
-- MySQL 8+ 优化器会自动转换，差别不大
```

### 2.2 相关子查询

```sql
-- 找出每个用户浏览量最高的文章
SELECT u.username, a.title, a.view_count
FROM user u
JOIN article a ON u.id = a.author_id
WHERE a.view_count = (
    SELECT MAX(a2.view_count)
    FROM article a2
    WHERE a2.author_id = u.id  -- 引用外层的 u.id，是"相关"子查询
);
```

### 2.3 派生表（FROM 子查询）

```sql
-- 统计每个用户的文章数和总浏览量，只取文章数 >= 3 的
SELECT t.username, t.article_count, t.total_views
FROM (
    SELECT
        u.username,
        COUNT(a.id)        AS article_count,
        SUM(a.view_count)  AS total_views
    FROM user u
    LEFT JOIN article a ON u.id = a.author_id
    GROUP BY u.id, u.username
) t
WHERE t.article_count >= 3
ORDER BY t.total_views DESC;
```

### 2.4 CTE（公用表表达式，MySQL 8.0+）

CTE 用 `WITH` 定义，比嵌套子查询可读性好得多：

```sql
-- 用 CTE 重写上面的查询
WITH user_stats AS (
    SELECT
        u.id,
        u.username,
        COUNT(a.id)        AS article_count,
        COALESCE(SUM(a.view_count), 0) AS total_views
    FROM user u
    LEFT JOIN article a ON u.id = a.author_id
    GROUP BY u.id, u.username
),
active_users AS (
    SELECT * FROM user_stats WHERE article_count >= 3
)
SELECT username, article_count, total_views
FROM active_users
ORDER BY total_views DESC;
```

```sql
-- 递归 CTE：查询分类树（所有子孙分类）
WITH RECURSIVE category_tree AS (
    -- 锚点：从指定分类开始
    SELECT id, name, parent_id, 0 AS level
    FROM category WHERE id = 1

    UNION ALL

    -- 递归：连接子分类
    SELECT c.id, c.name, c.parent_id, ct.level + 1
    FROM category c
    JOIN category_tree ct ON c.parent_id = ct.id
)
SELECT * FROM category_tree ORDER BY level, id;
```

## 3. 窗口函数

窗口函数（MySQL 8.0+）可以在不减少行数的情况下进行聚合计算，是数据分析的利器：

### 3.1 基本语法

```sql
函数名() OVER (
    PARTITION BY 分组字段    -- 按哪个字段分组（可省略）
    ORDER BY 排序字段         -- 窗口内的排序
    ROWS/RANGE 帧定义         -- 窗口大小（可省略）
)
```

### 3.2 排名函数

```sql
-- ROW_NUMBER()：连续排名（1,2,3,4...）
-- RANK()：有并列时跳号（1,2,2,4...）
-- DENSE_RANK()：有并列时不跳号（1,2,2,3...）

SELECT
    title,
    author_id,
    view_count,
    ROW_NUMBER() OVER (ORDER BY view_count DESC) AS row_num,
    RANK()       OVER (ORDER BY view_count DESC) AS rank_num,
    DENSE_RANK() OVER (ORDER BY view_count DESC) AS dense_rank
FROM article
WHERE status = 'PUBLISHED';

-- 按作者分组排名（每个作者内部排名）
SELECT
    title,
    author_id,
    view_count,
    RANK() OVER (PARTITION BY author_id ORDER BY view_count DESC) AS rank_in_author
FROM article;
```

### 3.3 取每组 Top N

```sql
-- 取每个作者浏览量最高的 2 篇文章
SELECT * FROM (
    SELECT
        a.*,
        ROW_NUMBER() OVER (
            PARTITION BY author_id
            ORDER BY view_count DESC
        ) AS rn
    FROM article a
    WHERE status = 'PUBLISHED'
) t
WHERE t.rn <= 2;
```

### 3.4 累计计算

```sql
-- 按月累计文章数和浏览量
SELECT
    DATE_FORMAT(created_at, '%Y-%m') AS month,
    COUNT(*)                          AS monthly_count,
    SUM(view_count)                   AS monthly_views,
    SUM(COUNT(*)) OVER (ORDER BY DATE_FORMAT(created_at, '%Y-%m')) AS cumulative_count
FROM article
WHERE status = 'PUBLISHED'
GROUP BY DATE_FORMAT(created_at, '%Y-%m')
ORDER BY month;
```

### 3.5 偏移函数

```sql
-- LAG/LEAD：访问前/后一行的值
SELECT
    DATE_FORMAT(created_at, '%Y-%m') AS month,
    COUNT(*)                          AS count,
    LAG(COUNT(*), 1) OVER (ORDER BY DATE_FORMAT(created_at, '%Y-%m')) AS prev_month_count,
    COUNT(*) - LAG(COUNT(*), 1) OVER (ORDER BY DATE_FORMAT(created_at, '%Y-%m')) AS growth
FROM article
GROUP BY DATE_FORMAT(created_at, '%Y-%m')
ORDER BY month;
```

## 4. 索引原理与设计

### 4.1 索引是什么

索引就像书的目录——没有目录要找某个内容需要翻遍全书（全表扫描），有了目录可以直接跳到对应页。

**B+ 树索引：**

```
MySQL InnoDB 使用 B+ 树存储索引：
- 所有数据存在叶子节点
- 叶子节点之间用双向链表连接（范围查询高效）
- 树高通常只有 3-4 层（千万级数据也能快速查找）

聚簇索引（主键索引）：叶子节点存放完整行数据
二级索引：叶子节点存放主键值（再通过主键回表查完整数据）
```

### 4.2 索引类型

```sql
-- 主键索引（自动创建）
PRIMARY KEY (`id`)

-- 唯一索引
UNIQUE KEY `uk_email` (`email`)

-- 普通索引
INDEX `idx_status` (`status`)

-- 复合索引（多列）
INDEX `idx_author_status` (`author_id`, `status`)

-- 全文索引（适合大段文本搜索）
FULLTEXT INDEX `ft_title_content` (`title`, `content`)
```

### 4.3 复合索引与最左前缀原则

```sql
-- 创建复合索引 (author_id, status, created_at)
INDEX `idx_author_status_time` (`author_id`, `status`, `created_at`)

-- ✅ 能用到索引（满足最左前缀）
WHERE author_id = 1
WHERE author_id = 1 AND status = 'PUBLISHED'
WHERE author_id = 1 AND status = 'PUBLISHED' AND created_at > '2026-01-01'

-- ❌ 不能用到索引（跳过了 author_id）
WHERE status = 'PUBLISHED'
WHERE created_at > '2026-01-01'

-- ⚠️ 部分使用（只能用到 author_id 部分）
WHERE author_id = 1 AND created_at > '2026-01-01'
-- author_id 能用索引，created_at 跳过了 status，不能用索引

-- 最左前缀：查询条件必须包含索引最左边的字段，才能用到索引
```

### 4.4 索引失效场景

```sql
-- ❌ 在索引列上使用函数
WHERE YEAR(created_at) = 2026           -- 改为范围查询
-- ✅ WHERE created_at BETWEEN '2026-01-01' AND '2026-12-31'

-- ❌ 隐式类型转换（字段是 VARCHAR，传了数字）
WHERE username = 123                    -- username 是 VARCHAR，123 会转换
-- ✅ WHERE username = '123'

-- ❌ LIKE 前缀通配符
WHERE title LIKE '%Spring%'             -- 前面有 % 无法用索引
-- ✅ WHERE title LIKE 'Spring%'        -- 只有后缀 % 可以用索引

-- ❌ OR 条件有非索引列
WHERE status = 'PUBLISHED' OR content LIKE '%hello%'  -- content 没索引，全表扫描

-- ❌ NOT IN / != 通常不走索引
WHERE status != 'DRAFT'                 -- 可以考虑改为 IN 其他状态值

-- ❌ 索引列参与计算
WHERE id + 1 = 10                       -- 改为 WHERE id = 9
```

### 4.5 索引设计原则

```
1. 频繁出现在 WHERE、JOIN ON、ORDER BY 的字段建索引
2. 区分度高的字段适合建索引（如 email，而不是 status 这种只有几个值的字段）
3. 复合索引把区分度高的字段放左边
4. 索引不是越多越好（每个索引都会占空间，写操作时需要维护）
5. 字段值太长的（如 TEXT）不适合直接建索引，可以建前缀索引
6. 每张表索引控制在 5 个以内
```

## 5. EXPLAIN 执行计划

`EXPLAIN` 是分析 SQL 性能的核心工具：

```sql
EXPLAIN SELECT a.title, u.username
FROM article a
JOIN user u ON a.author_id = u.id
WHERE a.status = 'PUBLISHED'
ORDER BY a.created_at DESC
LIMIT 10;
```

**关键字段说明：**

| 字段      | 含义           | 好的值                                      |
| --------- | -------------- | ------------------------------------------- |
| `type`    | 访问类型       | `const` > `ref` > `range` > `index` > `ALL` |
| `key`     | 实际使用的索引 | 有值（不是 NULL）                           |
| `key_len` | 索引长度       | 越短越好                                    |
| `rows`    | 预估扫描行数   | 越少越好                                    |
| `Extra`   | 额外信息       | 避免 `Using filesort`、`Using temporary`    |

**type 各值含义：**

```
const   ：主键或唯一索引等值查询，最快，只返回 1 行
eq_ref  ：JOIN 时使用主键或唯一索引
ref     ：使用非唯一索引
range   ：索引范围扫描（BETWEEN、>、<、IN）
index   ：遍历整个索引树（比 ALL 好一点）
ALL     ：全表扫描，最慢，大表要避免
```

```sql
-- 示例：分析查询
EXPLAIN SELECT * FROM article WHERE status = 'PUBLISHED';
-- 如果 type = ALL，说明 status 没有索引或索引失效

-- 添加索引后再看
ALTER TABLE article ADD INDEX idx_status (status);
EXPLAIN SELECT * FROM article WHERE status = 'PUBLISHED';
-- type 应该变成 ref
```

## 6. 慢查询优化

### 6.1 开启慢查询日志

```sql
-- 查看当前配置
SHOW VARIABLES LIKE 'slow_query%';

-- 临时开启（重启后失效）
SET GLOBAL slow_query_log = ON;
SET GLOBAL long_query_time = 1;  -- 超过 1 秒的查询记录到日志
```

### 6.2 常见优化手段

**优化 1：加合适的索引**

```sql
-- 慢查询：
SELECT * FROM article WHERE author_id = 1 ORDER BY created_at DESC LIMIT 10;
-- EXPLAIN 显示 type=ALL

-- 优化：添加复合索引
ALTER TABLE article ADD INDEX idx_author_time (author_id, created_at);
-- 现在 type=ref，rows 从全表降到几行
```

**优化 2：避免 SELECT \***

```sql
-- ❌ 查出所有字段，包含大文本 content
SELECT * FROM article WHERE status = 'PUBLISHED' LIMIT 10;

-- ✅ 只查需要的字段，避免传输大文本
SELECT id, title, summary, author_id, created_at
FROM article WHERE status = 'PUBLISHED' LIMIT 10;
```

**优化 3：分页大偏移量问题**

```sql
-- ❌ 深分页性能很差（扫描了 10000+10 行）
SELECT * FROM article ORDER BY id DESC LIMIT 10000, 10;

-- ✅ 用游标分页（记住上一页最后一条的 id）
SELECT * FROM article
WHERE id < 最后一条的id
ORDER BY id DESC
LIMIT 10;
```

**优化 4：COUNT 优化**

```sql
-- 统计总数时，用 COUNT(1) 或 COUNT(id) 而不是 COUNT(*)
-- 实际上 MySQL 优化器对这三种写法处理一样，差别不大
-- 但 COUNT(字段) 会排除 NULL，和 COUNT(*) 含义不同，注意区分

SELECT COUNT(1) FROM article WHERE status = 'PUBLISHED';
```

**优化 5：JOIN 优化**

```sql
-- 小表驱动大表：把结果集小的表放在 JOIN 的左边（驱动表）
-- MySQL 优化器通常会自动选择，但数据量相差悬殊时可以用 STRAIGHT_JOIN 强制

-- 确保 JOIN 的关联字段都有索引
-- ON a.author_id = u.id → author_id 和 u.id 都应该有索引
```

## 7. 数据库设计范式

### 7.1 第一范式（1NF）：字段原子性

```sql
-- ❌ 违反 1NF：tags 是多值字段
CREATE TABLE article (
    id    INT,
    title VARCHAR(100),
    tags  VARCHAR(200)  -- "Java,Spring,MySQL" 多个值存在一个字段
);

-- ✅ 符合 1NF：拆分为关联表
CREATE TABLE article_tag (
    article_id INT,
    tag_id     INT
);
```

### 7.2 第二范式（2NF）：消除部分依赖

每个非主键字段完全依赖于主键（在有复合主键时才需要考虑）。

### 7.3 第三范式（3NF）：消除传递依赖

```sql
-- ❌ 违反 3NF：author_name 依赖于 author_id，不直接依赖于 article.id
CREATE TABLE article (
    id          INT,
    title       VARCHAR(100),
    author_id   INT,
    author_name VARCHAR(50)  -- 传递依赖：article → author_id → author_name
);

-- ✅ 符合 3NF：author 信息放到 user 表，通过 JOIN 查询
CREATE TABLE article (
    id        INT,
    title     VARCHAR(100),
    author_id INT  -- 只存 ID，名字通过 JOIN 获取
);
```

### 7.4 反范式设计（冗余换性能）

严格遵守范式有时会导致大量 JOIN，影响查询性能。实际项目中**适当冗余**是常见做法：

```sql
-- 在 article 表里冗余存 author_name
-- 好处：查文章列表不需要 JOIN user 表
-- 代价：用户改名时需要同步更新所有文章的 author_name（用消息队列异步处理）

ALTER TABLE article ADD COLUMN author_name VARCHAR(50) COMMENT '冗余存储的作者名';
```

**原则：** 先按范式设计，再根据实际查询性能决定是否引入冗余。

## 常见问题

**Q：INNER JOIN 和 WHERE 有什么区别？**  
A：`INNER JOIN ... ON` 和 `WHERE` 在语义上对 INNER JOIN 来说结果相同，但习惯上 JOIN 条件写在 ON 里，过滤条件写在 WHERE 里，可读性更好。对 LEFT JOIN 来说，把条件写在 WHERE 里会把 LEFT JOIN 变成 INNER JOIN（因为 WHERE 会过滤掉 NULL 行）。

**Q：什么情况下建复合索引比多个单列索引好？**  
A：当查询经常同时用到多个字段过滤时，复合索引比多个单列索引更高效（一次索引扫描 vs 多次），且能覆盖索引（不需要回表）。但复合索引要注意最左前缀，设计时把最常用、区分度最高的字段放最左。

**Q：`EXPLAIN` 里的 `Using filesort` 是什么意思，如何避免？**  
A：说明 MySQL 无法用索引完成排序，需要额外的排序步骤（在内存或磁盘上），性能较差。避免方法：确保 ORDER BY 的字段有索引，且排序方向（ASC/DESC）与索引一致。如果是 GROUP BY 后再 ORDER BY，把 ORDER BY 的字段也加入复合索引。

**Q：`COUNT(*)` 、`COUNT(1)` 、`COUNT(id)` 哪个最快？**  
A：在 MySQL InnoDB 中，三者性能基本相同，优化器会自动选最优方式。但语义不同：`COUNT(*)` 统计所有行（包含 NULL），`COUNT(字段)` 统计非 NULL 的行。大多数情况用 `COUNT(*)` 就行。
